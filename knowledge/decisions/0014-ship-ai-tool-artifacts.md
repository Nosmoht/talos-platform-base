# ADR: Ship tool-generated AI artifacts in the base

## Context and Problem Statement

Until this decision the base documented a strict policy: it ships no
`.claude/` tree and no Claude-Code-specific primitives (`CLAUDE.md`
§Claude-Code-Specific Additions, the `.gitignore` blanket ignore, and
`AGENTS.md` §Domain Rules). Adopting OpenSpec (`base:openspec-adoption`)
surfaces a conflict: `openspec init` generates editor integrations — skill
and command trees for Claude Code and Codex — that every contributor needs
for the `/opsx:*` spec-driven workflow. Keeping them uncommitted forces
every operator to regenerate locally and lets integration versions drift
silently. The owner has ruled the blanket policy wrong: this repo may ship
AI tooling.

## Decision Drivers

- One consistent, versioned spec-driven workflow for every contributor and
  agent, not per-workstation regeneration drift.
- The artifacts are tool-GENERATED and fully regenerable (`task
  spec:update`) — committing them carries no hand-maintenance burden.
- Operator scratch state (local settings, worktrees) must stay out of the
  public repo.
- The published OCI artifact must stay unaffected (consumers vendor the
  substrate, not repo tooling).

## Considered Options

1. Keep the blanket "no AI-tool trees" policy; every operator regenerates
   locally.
2. Commit exactly the tool-generated, regenerable artifacts; keep
   hand-authored harness primitives external (selective reversal).
3. Open the repo to arbitrary committed harness content (full reversal).

## Decision Outcome

Chosen option: **selective reversal (option 2)**. The Claude Code and
Codex trees generated by `openspec init`/`openspec update` are committed;
operator scratch under `.claude/` stays gitignored via selective negation
(`.claude/*` + explicit `!` entries). Hand-authored rules, hooks, and
subagents remain external-harness territory as before.

### Consequences

- Positive: the `/opsx:*` workflow works identically on every checkout;
  integration upgrades are reviewable diffs.
- Negative: the "regenerable-only" boundary is a documented convention —
  gitignore cannot distinguish generated from hand-dropped files inside an
  un-ignored directory. A hand-authored file placed in a committed
  generated tree WILL be overwritten or orphaned by the next `task
  spec:update`; do not hand-edit these trees.
- Negative: generated markdown is exempted from markdownlint (linting
  would fight the generator on every upgrade).
- Follow-up: `task spec:update` fails when a regeneration emits paths the
  gitignore negation list does not cover, so newly generated content can
  never be silently ignored.

## Pros and Cons of the Options

### Option 1 — keep the blanket policy

- Pro: zero committed tool surface; strictest layering.
- Con: per-workstation drift; the spec-driven workflow the owner wants
  becomes optional equipment.

### Option 2 — selective reversal (chosen)

- Pro: consistency with reviewability; scratch stays private.
- Con: convention-enforced boundary (see Consequences).

### Option 3 — full reversal

- Pro: maximal flexibility.
- Con: invites hand-authored, unreviewed harness content into a public
  base; contradicts the external-harness architecture without need.

## Validation

The decision is wrong if generated-tree diffs start requiring hand edits
to keep working. Mechanical checks: `task spec:update` regenerates
cleanly and its gitignore-completeness gate stays green; the OCI
allowlist (`.ci-oci-tarball-include.txt`, fail-closed expected-diff)
keeps every AI-tool tree out of the published artifact.
