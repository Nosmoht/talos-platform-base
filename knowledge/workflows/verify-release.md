# Verify a Base Release

Every git tag `v*` pushed to the base triggers `oci-publish.yml`, which
publishes a signed, attested OCI artifact to
`ghcr.io/nosmoht/talos-platform-base:<tag>`. Consumers must verify signature,
provenance, and SBOM before vendoring; failure of any step is fail-closed —
do not vendor.

## What the publish workflow actually does

The trust chain, in workflow order:

1. **Allowlist tarball build.** The tarball is built with
   `tar -czf talos-platform-base-<tag>.tar.gz --files-from=.ci-oci-tarball-include.txt`
   — only paths listed in
   `.ci-oci-tarball-include.txt` are packaged; anything not listed is excluded
   by default (allowlist beats blocklist).
2. **Contents fixture diff.** The tarball listing is diffed against the
   committed `.ci-oci-tarball-expected.txt`; any divergence fails the build.
3. **Checksums.** `sha256sum *.tar.gz > checksums.txt`.
4. **OCI push.** `oras push` with artifact type
   `application/vnd.talos-platform-base.v1+tar`, carrying two layers: the
   tarball (`application/gzip`) and `checksums.txt` (`text/plain`).
5. **Digest capture.** `oras manifest fetch --descriptor | jq -r .digest` —
   all attestations key on this digest, not the mutable tag.
6. **cosign sign (keyless OIDC).** `cosign sign --yes ghcr.io/...@<digest>`,
   anchored to the workflow's GitHub OIDC token identity (workflow ref,
   repository, tag).
7. **SLSA build provenance.** `actions/attest-build-provenance@v1` with
   `push-to-registry: true` — proves which commit, runner, and inputs built
   the artifact.
8. **CycloneDX 1.6 SBOM.** Generated by Syft (`anchore/sbom-action@v0.17.9`)
   over the tarball as `talos-platform-base-<tag>.cdx.json`, then attached
   with `cosign attest --yes --type cyclonedx` keyed to the digest.
9. **`:latest` tag** — only for non-hyphenated tags; SemVer pre-releases
   (`v*-*`) never become `:latest`.
10. **GitHub Release.** Created as a draft, the tarball, `checksums.txt`, and
    the SBOM JSON attached to it, then published — release immutability
    freezes a release at publish time and a published one rejects asset
    uploads, so the draft window is the only place the assets can be attached.
    Hyphenated tags are marked pre-release. ghcr.io remains the authoritative,
    signed consumption path.
11. **Asset assertion.** The draft's assets are verified before it is
    published, and the published release is read back afterwards through the
    tag endpoint a consumer browsing the Releases page sees; either mismatch
    fails the workflow and opens a tracking issue.

## Releases without assets

Seven published releases carry **no** Release assets, and a published release
is immutable, so none of them can be backfilled. They split into two groups
that need different handling — do not treat the list as uniform:

**Artifact intact, assets missing** — `v9.2.2`, `v9.2.3`, `v10.0.0`,
`v11.0.0`, `v11.0.1`. The release object was already published by
semantic-release, so every asset upload was refused with HTTP 422 (#251). The
OCI artifacts are published, signed, and attested normally: consume these tags
via `oras pull` and the digest, exactly as the recipe below documents. Only the
Release-asset download path is missing.

**Nothing published at all** — `v9.1.2`, `v9.2.0`. These failed earlier, at
the `oras` install step, which is upstream of the push: there is no artifact,
no signature, and no attestation, and
`ghcr.io/nosmoht/talos-platform-base:<tag>` returns 404 for both (verified
2026-09-04). They are git tags with a GitHub Release object and nothing else.
**Do not pin them.** `v9.2.1` and `v9.1.1` are the intact tags on either side.

Tags from the fix onward carry all three assets, asserted in the publish
workflow itself. Recovery procedure and why it is forward-only:
[release-process](./release-process.md) §A release that shipped without
assets.

## The signing identity

All three attestations are anchored to the GitHub OIDC identity of the
publishing workflow:

- **Certificate OIDC issuer:** `https://token.actions.githubusercontent.com`
- **Certificate identity:** the workflow ref
  `https://github.com/Nosmoht/talos-platform-base/.github/workflows/oci-publish.yml@refs/tags/<tag>`

The identity regexp below pins the repository, the exact workflow file, and a
release-shaped tag (`vX.Y.Z`), so a signature from a fork, another workflow,
or a pre-release tag does not verify. The workflow triggers on any `v*` tag
and signs with the actual tag ref, so for deliberate testing of a pre-release
artifact append an optional `(-[A-Za-z0-9.-]+)?` suffix to the tag part of the
regexp — keep the strict release form for production consumers.

## The verification recipe (consumer side)

Run all steps in your own CI before any vendored base reaches a live cluster.

### 1. Verify the signature

```bash
TAG=v1.0.0
cosign verify \
  --certificate-identity-regexp \
    "^https://github.com/Nosmoht/talos-platform-base/\\.github/workflows/oci-publish\\.yml@refs/tags/v[0-9]+\\.[0-9]+\\.[0-9]+$" \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "ghcr.io/nosmoht/talos-platform-base:${TAG}"
```

### 2. Pin the digest

Resolve the manifest digest once and use it for every subsequent step — the
same command the workflow itself uses to key its attestations:

```bash
DIGEST=$(oras manifest fetch --descriptor \
  "ghcr.io/nosmoht/talos-platform-base:${TAG}" | jq -r .digest)
```

### 3. Verify SLSA build provenance

The provenance is pushed to the registry by
`actions/attest-build-provenance`; verify it with the GitHub CLI:

```bash
gh attestation verify \
  "oci://ghcr.io/nosmoht/talos-platform-base:${TAG}" \
  --repo Nosmoht/talos-platform-base
```

Check the reported source commit matches the git tag you expect.

### 4. Verify the SBOM attestation

The SBOM attestation ships on `v0.6.0` and later (per `SECURITY.md`); older
tags carry signature + provenance only.

```bash
cosign verify-attestation \
  --type cyclonedx \
  --certificate-identity-regexp \
    "^https://github.com/Nosmoht/talos-platform-base/\\.github/workflows/oci-publish\\.yml@refs/tags/v[0-9]+\\.[0-9]+\\.[0-9]+$" \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "ghcr.io/nosmoht/talos-platform-base@${DIGEST}"
```

### 5. Pull by digest and check the tarball checksum

```bash
oras pull "ghcr.io/nosmoht/talos-platform-base@${DIGEST}" --output vendor/base/
(cd vendor/base && sha256sum -c checksums.txt)
```

`checksums.txt` is generated inside the same workflow run that built the
tarball, so this binds the bytes on disk to the signed, attested digest.

### 6. (Optional) audit the contents

The exact expected membership is version-controlled as
`.ci-oci-tarball-expected.txt` in the base repo at the same tag:

```bash
tar -tzf "vendor/base/talos-platform-base-${TAG}.tar.gz" \
  | sed 's|^\./||' | LC_ALL=C sort | sed 's|^|./|' \
  | diff -u .ci-oci-tarball-expected.txt -
```

## Producer-side fixture check

Before pushing a tag, a maintainer confirms the allowlist and fixture agree
with the working tree — the local equivalent of workflow steps 1–2:

```bash
task supply-chain:oci-allowlist
```

It builds the tarball from `.ci-oci-tarball-include.txt` into `.work/`, diffs
the listing against `.ci-oci-tarball-expected.txt`, and fails on any
divergence. Intentional membership changes update both files together
(`mv .work/oci-check-contents.txt .ci-oci-tarball-expected.txt`); the CI
"Verify tarball contents" step catches anything that slips through. See
[release-process](./release-process.md) for the full tagging flow.

## Failure policy

Fail-closed, every step:

- Signature does not verify against the identity regexp + issuer → do not vendor.
- Provenance missing or pointing at an unexpected commit/repo → do not vendor.
- SBOM attestation missing → do not vendor.
- `sha256sum -c` mismatch → do not vendor.

Pin `vendor/base/` consumption to the pinned `@<digest>`, not the `<tag>`.
The digest is the only thing that prevents tag reassignment from silently
changing what you vendor: the GitHub Container registry offers no immutable-tag
setting, so a `v*` tag there can be moved onto a different image. Repository
releases are immutable (the git tag and its release assets cannot be replaced),
which covers the release object but not the published image.
